# Payments and e-invoicing matrix

Per supported region: which local payment methods matter, what a valid tax invoice must contain, and whether e-invoicing is mandated. Not legal advice. **Every cell is [VERIFY]** and anything legal is **[COUNSEL]**: the rows are starting hypotheses written by engineering, not findings, and they stay that way until a row carries a primary source, a reviewer and a counsel reviewer.

## Scope

* "Region" means a regional pack (US, CA, GB, EU, AU); the table has one row per country (31). EU rows matter individually because invoice content and e-invoicing mandates are national.
* Covers the invoices Vireek issues for its own subscription charges and the customer invoices tenants generate through Vireek. **[COUNSEL]** to confirm which flows each market actually requires.
* Today Vireek checks invoice data against local mandatory content (`src/lib/regionalPacks/packDocuments.ts`) but does not produce e-invoice XML or connect to any national system. Every row therefore starts with `vireekSupport: none`.

## The billing gate

A non-default region cannot be enabled for billing until its rows are complete.

1. **Config**: `config/global/payments-einvoicing.json`, one row per country.
2. **Completeness** (a row is complete only when all hold): at least one local method; tax-invoice requirements written; e-invoicing B2B and B2G decided (not `unknown`); Vireek support assessed; if either is `mandatory` or `phased`, a `system` is named and support is `implemented` or a `workaround` is written; `verification.status` is `verified` with an https `source`, `reviewer`, `counselReviewer` and both dates real, not in the future and not older than `verificationMaxAgeDays` (365).
3. **Pack complete** = all its countries complete. EU therefore needs all 27.
4. **Database**: `set_regional_pack(pack, true)` refuses a non-US pack unless `billing_region_clearances` holds a cleared row for it (migration `20290311000000_billing_region_gate.sql`). The row can only be written by Vireek staff through `staff_set_billing_region_clearance`, which requires the pack hash, the verifier, the counsel reviewer and their dates. US is the default region and is never blocked. Packs a tenant already enabled keep working; disabling is always allowed.
5. **CI**: `npm run payments-einvoicing:check` validates the file and fails when this document is out of date.

Commands:

```bash
npm run payments-einvoicing:report                    # which packs/rows are complete and what is missing
npm run payments-einvoicing:report -- --pack GB --strict   # exit 3 while GB is incomplete
npm run payments-einvoicing:hash -- GB                # sha256 to give the clearance RPC
npm run payments-einvoicing:write                     # regenerate the table below after editing the JSON
npm run test:scripts:payments-einvoicing
```

## Verifying a row

1. Check each cell against the tax authority, the payment scheme or the processor documentation (not a blog) and put the page in `verification.source`.
2. Replace hypotheses with the verified text. Methods outside the code list are marked "not in code": they are a product gap, not a blocker, unless the row says they are required.
3. Counsel signs the tax-invoice and e-invoicing cells; record the name and date.
4. Set `status` to `verified`, run `payments-einvoicing:write`, then `payments-einvoicing:report -- --pack <PACK>`.
5. When the pack is complete, a staff member runs the clearance RPC (see the migration header) with `npm run payments-einvoicing:hash -- <PACK>`. Editing any row afterwards changes the hash; re-clear before relying on it.
