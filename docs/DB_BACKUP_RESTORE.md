# Backup / Restore: وضعیت واقعی، RTO و RPO

**هیچ عدد RTO/RPO در این سند اندازه‌گیری نشده است.** جدول آخر را فقط بعد از انجام روال اندازه‌گیری پر کنید.

## لایه‌ها (از روی کد ریپو)

| لایه | چه چیزی را پوشش می‌دهد | محدودیت‌ها |
|---|---|---|
| Supabase PITR / backup فیزیکی | کل دیتابیس | تنظیم و نگهداری آن در ریپو تأیید نشده. باید در Dashboard → Database → Backups بررسی شود (پلن، retention، چه کسی restore می‌زند). |
| `dr-backup-run` (backup منطقی) | فقط `OWNED_TABLE_NAMES` + `profiles`, `team_members`, `customers`، یعنی حدود ۱۷ جدول از حدود ۱۵۰۰ جدول | کل داده در حافظه‌ی یک edge function به JSON تبدیل و gzip می‌شود، پس با رشد داده محدودیت حافظه/زمان می‌گیرد. جدول‌های پرحجم (telemetry, notifications, audit، …) داخلش نیستند. RPO این لایه = فاصله‌ی اجرای cron، فقط برای همان جدول‌ها. |
| `dr-restore-drill` | checksum + شمارش ردیف + restore نمونه (حداکثر ۳ جدول × ۵۰۰ ردیف) در یک schema موقت | `rto_seconds` فقط زمان دانلود + checksum + gunzip + نمونه‌گیری است، **نه زمان بازیابی واقعی**. این عدد را به‌عنوان RTO گزارش نکنید. |

## روال اندازه‌گیری RTO واقعی
1. در staging (یا یک Supabase branch/پروژه‌ی جدید) از آخرین backup فیزیکی/PITR یک restore کامل بزنید و زمان را از لحظه‌ی درخواست تا لحظه‌ای که health-check برنامه (`/status` و یک login واقعی) سبز می‌شود ثبت کنید.
2. با `perf.table_health` و شمارش ردیف چند جدول کلیدی، کامل بودن داده را بعد از restore تأیید کنید.
3. برای RPO: یک ردیف مارکردار در `audit_log` بنویسید، زمان را ثبت کنید، PITR را به چند دقیقه‌ی بعد از آن برگردانید و ببینید ردیف هست یا نه. کوچک‌ترین فاصله‌ی قابل‌اثبات = RPO اندازه‌گیری‌شده.
4. روال را هر سه ماه و بعد از هر تغییر بزرگ حجم تکرار کنید.

## کارهای پیشنهادی (انجام‌نشده)
- جداکردن `rto_seconds` در drill به `verification_seconds` تا گمراه‌کننده نباشد (نیاز به مایگریشن روی `platform_restore_drills` و تأیید ساختار جدول).
- افزودن جدول‌های حیاتی بیشتر به backup منطقی یا حذف وابستگی به آن به نفع PITR.
