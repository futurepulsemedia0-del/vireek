# Feedback-to-roadmap log (template)

One row per distinct piece of feedback. Keep it where product and support can both see it. The log is the source for "you said / we did" — never summarise from memory.

## Columns
| Column | Meaning |
|---|---|
| ID | `CAB-<YYYY>-<NNN>` |
| Date | Session or channel date |
| Source | Member (or "Anonymous"), session, working group, pulse |
| Verbatim / paraphrase | What was said; mark which |
| Workflow / area | e.g. dispatch, quoting, calls, billing |
| Evidence | Concrete example, frequency, cost to the member; "none" is allowed |
| Segment | Trade / size band of the member |
| Corroboration | Other members, support tickets, usage data that agree or disagree (links) |
| Impact (H/M/L) + reason | Written reason, not a guess presented as fact |
| Effort (S/M/L) or "unknown" | From engineering, not from product alone |
| Decision | Accepted / Planned / Parked / Declined / Already exists / Needs research |
| Decision reason | Required for every decision, especially Declined and Parked |
| Roadmap link | Issue / epic / release note, once it exists |
| Owner | Named person |
| Decision date | Within the charter window (`<30>` days) |
| Communicated | Date and channel the member was told |
| Outcome | Shipped / not shipped, date, link — filled in later |

## Rules
1. Every item gets a decision and a reason, including "declined". Silence is not an answer.
2. Priority comes from evidence across customers, not from who was loudest or most senior.
3. Do not log other people's personal data or a member's confidential business data beyond what the item needs.
4. A decision is not a delivery date. Status words must not imply a commitment.
5. If an item changes the roadmap, link the change; if it does not, say why.
6. Review the log at each session start and at the annual review: items older than `<60>` days without a decision are escalated to the executive sponsor.
7. Member-visible view shows only that member's items plus anonymised, aggregated themes.
