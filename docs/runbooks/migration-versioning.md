# Runbook — migration versioning safety

Status: **proposed rule for DECISIONS_NEEDED D-11 / RUNBOOK §8-2 — needs owner approval** · Guard: `scripts/migrations/check-migration-versioning.mjs`
Related: `docs/runbooks/migration-version-repair.md` (duplicate prefixes, `scripts/migrations-dedupe.mjs`), ADR-0010.

## 1. Why this matters (the ordering risk)

Supabase records one row per migration in `supabase_migrations.schema_migrations`; the 14-digit prefix is the primary key and the
CLI applies files in **bytewise filename order**. Consequences:

1. **Duplicate versions** (two files, same prefix) break `db reset` / `db push` (primary-key conflict).
2. **Irregular names** (8-digit prefix, `.sq` typo, `<timestamp>_…` placeholder, stray directories) are skipped by the CLI or recorded under a
   wrong version. A skipped migration is *never applied* and nobody notices.
3. **Future-dated versions** (the tree contains versions years ahead of the calendar) sort *after* any migration created today with
   `supabase migration new` (which stamps the real current time). A migration created today therefore sorts **before** already-applied
   migrations: on a database that has them, `supabase db push` refuses to insert it before the last applied version (the CLI asks for
   `--include-all`; **[VERIFY]** exact behaviour and flag in the CLI version you run), and on a fresh `db reset` it replays *earlier* than
   migrations it may depend on. Same hazard between two parallel PRs.
4. Renaming or editing an applied migration desynchronises every environment that already recorded the old version.

## 2. The rule for new versions

| # | Rule | Enforced by CI as |
|---|---|---|
| R1 | File name is exactly `<14-digit UTC timestamp YYYYMMDDHHMMSS>_<snake_case>.sql`, a real calendar date | `irregular-name` |
| R2 | The version is unique across the directory | `duplicate-version` |
| R3 | A new migration's version is **strictly greater than every migration already on the base branch** | `out-of-order` |
| R4 | …and is **not more than one day beyond `max(latest existing version, now)`** — continue the sequence, never jump ahead | `future-jump` |
| R5 | Applied migrations are never edited, renamed or deleted (fix forward with a new migration) | `edited-applied` / `renamed-applied` / `deleted-applied` |
| R6 | Get the version with `node scripts/migrations/check-migration-versioning.mjs next` and create the file by hand | — |

While legacy future-dated files exist, R3 means a new migration must also be "in the future" (the `next` command returns
`max(existing)+1s`). That is deliberate: **ordering safety outranks calendar honesty**. Do **not** use `supabase migration new` until
the repair plan (§5) has run, because its real-time stamp violates R3. After the repair, `next` returns the current UTC time again.

## 3. What the CI guard does

`node scripts/migrations/check-migration-versioning.mjs check --base origin/main` fails **only on new violations**:

* Legacy violations are frozen in `scripts/migrations/versioning-baseline.json` (generated by `baseline --write`; reviewed in a PR).
  A new file that joins a baselined duplicate group is a *new* violation; the old members stay silent.
* Future-dated files **past the baseline's `maxVersion`** are the compliant "frontier" (R3/R4 govern them), not legacy debt.
* With `--base`, "new" = not present on the base ref and edits/renames/deletes are detected through `git diff`. Without `--base` it falls
  back to the baseline snapshot (local use only; edit detection is skipped).
* Baselined entries that no longer violate are listed as `ℹ stale` (never a failure). Prune them in a reviewed PR.
* Exit codes: 0 ok · 1 violations · 2 usage/I-O/git error.

Commands: `report` (audit counts) · `baseline [--write]` · `next` · `repair-plan` (prints, never executes) · `check`.
Tests: `npm run test:scripts:migrations`.

### One-time setup
```bash
node scripts/migrations/check-migration-versioning.mjs report          # audit: counts, duplicates, irregular names
node scripts/migrations/check-migration-versioning.mjs baseline --write # writes scripts/migrations/versioning-baseline.json
git add scripts/migrations/versioning-baseline.json                     # review the diff: it must contain ONLY today's legacy state
```
Regenerating the baseline later hides new problems: do it only in a dedicated, reviewed PR.

## 5. Repair plan (documented only — **nothing below has been executed**)

Prerequisites for every already-migrated environment: a fresh backup; a deploy freeze; `supabase link --project-ref <ref>`;
`supabase migration list` saved; `supabase db diff --linked` shows no drift for the objects these migrations create. If objects are
missing, do **not** repair — apply the missing migrations with `supabase db push` instead. Never mark a migration `applied` if its SQL did not run there.
Do staging first, production only after staging is verified. Renaming applied files is the one sanctioned exception to R5; open the PR with
the label `migration-repair` and run the guard with `--repair-pr` (allows rename/delete of baselined files only, never edits).

**Phase 1 — irregular names (manual).** For each name from `report`: if a `.sql` twin exists, `diff` both and keep one; fix `.sq`→`.sql`;
8-digit prefixes → 14 digits; replace the `<timestamp>` placeholder with a real version after confirming the file was never applied; decide
what `split/` is (it is not a migration). Only files that were never recorded remotely may be renamed freely.

**Phase 2 — duplicate versions.** Use the existing tool (order-preserving):
```bash
node scripts/migrations-dedupe.mjs plan        # review (dry run)
node scripts/migrations-dedupe.mjs apply       # renames + writes supabase/migration-renumber-map.json
node scripts/migrations-dedupe.mjs repair-script > repair.sh   # review; run per environment (see migration-version-repair.md)
```

**Phase 3 — future-dated versions.** Print the plan (read-only):
```bash
node scripts/migrations/check-migration-versioning.mjs repair-plan > repair-future.sh   # review it, do not run blindly
```
It compresses every future-dated migration into the seconds right after the newest non-future version, preserving execution order, and
refuses if there is no room before "now" or if duplicates remain. Its output has two parts:
```bash
# A) in a branch
git mv supabase/migrations/<old>.sql supabase/migrations/<new>.sql          # one per future-dated file
# B) per already-migrated environment, in chunks of 20 versions
supabase migration repair --status reverted <old versions…>                 # drops the stale history rows
supabase migration repair --status applied  <new versions…>                 # records the same SQL under its new version
supabase migration list                                                      # Local and Remote must match row for row
supabase db push --dry-run                                                   # must say the remote database is up to date
```
Before merging Phase 3 run `grep -rn "<old version or file name>" .` for scripts, docs, tests or code that reference migration file names
(`scripts/gen-*-migration.mjs`, pgTAP files, docs) and update them.

**Phase 4 — close out.** `supabase db reset` locally must finish without errors; regenerate the baseline (now empty of legacy entries);
remove `--repair-pr`; switch the team back to `supabase migration new`; mark D-11 resolved.

### Rollback
Restore the backup, or invert: `supabase migration repair --status reverted <new versions>` then `--status applied <old versions>`, and
`git revert` the rename commit. Re-running any repair command is idempotent.

## 6. Do / don't
* Do get versions from `next`; rebase and renumber your migration if another PR merged a later one first (R3 will tell you).
* Don't edit an applied migration — add a new one. Don't reuse a version. Don't hand-edit `schema_migrations`.
* Mark legal/compliance implications **[COUNSEL]** and unverified CLI behaviour **[VERIFY]** in PR descriptions.
